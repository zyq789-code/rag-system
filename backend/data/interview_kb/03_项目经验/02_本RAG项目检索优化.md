## 项目：RAG 知识库 —— 中文检索质量与性能优化

### 遇到的问题
1. 原始 BM25 用空格分词，中文整句变成一个大 token，关键词检索基本失效
2. 每次查询都全量拉取向量库语料并重建索引，延迟随语料规模线性增长
3. **重排模型失效**：原用英文 cross-encoder/ms-marco-MiniLM-L-6-v2 对中文打分，结果近乎随机——向量检索和 BM25 都排对的文档，重排后反而被挤出 top5

### 优化方案
**检索质量**
- 引入 jieba 中文分词 + 停用词过滤，中文按词切分
- 修正 top_k_bm25 配置未生效的 bug（原来误用了 top_k_vector）
- **重排模型换成中文优化的 maidalun1020/bce-reranker-base_v1**，重排真正起作用
- 形成"向量 + 中文 BM25 → RRF 融合 → 中文重排序"的完整链路

**检索性能**
- 语料缓存：VectorStore 增加 TTL 缓存 + texts_revision 版本号
- 索引缓存：BM25 索引按版本号重建，文档变更才重建，稳态查询只打分
- 增删文档时显式失效缓存，跨进程由 TTL 兜底

### 量化结果
- 真实知识库评测（22 个问题，3 个知识库，22 篇文档）：
  - 修复前：hit@1 = 63.6%，MRR = 68.9%
  - 修复后：**hit@1 = 100%，MRR = 100%**
- 中文检索 hit@1 从 12.5% 提升至 100%（合成演示语料）
- 索引重建成本从"每查询支付"变为"仅文档变更时一次"（5 万块约 7.6s → 0）
- 测试：新增 BM25 专项测试，项目 34 项全部通过

### 我的收获
1. 检索优化的核心是"先建立评测，再谈优化"——没有 hit@k/MRR 数字，一切优化都是主观判断
2. 重排/向量模型必须与语料语言匹配，模型选型错误比参数错误影响更大
3. 评测流程（evaluate_rag.py + 问题集）让每一次改动都可量化、可回归

> 面试重点：这页是"有方法"的证据——发现问题→定位根因→改进→量化验证，是完整闭环。
