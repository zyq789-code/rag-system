# RAG 智能知识库问答系统 · 检索质量与性能优化报告

> 项目：基于 RAG（检索增强生成）架构的中文知识库问答系统
> 技术栈：FastAPI + ChromaDB + PostgreSQL + Celery + Vue3 + sentence-transformers
> 报告日期：2026-08

---

## 1. 项目背景

本项目实现文档上传 → 解析分块 → 向量化入库 → 混合检索 → LLM 流式回答的完整闭环。在初版功能可用后，发现**中文检索质量与查询性能**存在明显短板，本报告记录从「建立评测」到「定位问题」再到「修复验证」的完整优化过程。**所有结论均有可复现的评测数据支撑，未做任何主观美化。**

## 2. 优化目标

1. 提升中文检索召回质量（当前 BM25 基于空格分词，中文不切词、召回差）
2. 降低查询延迟（当前每次查询都全量拉取向量库并重建索引）
3. 建立可量化的评测体系，让每一次改动可回归

## 3. 评测体系建设（先行，这是本次优化的前提）

优化之前，先建立两套评测手段——**没有数字，一切优化都是主观判断**。

### 3.1 离线检索基准 `backend/scripts/benchmark_retrieval.py`

- 自包含、离线、可复现，无需外部服务
- 对比「旧 BM25（空格分词）」vs「新 BM25（jieba 分词）」的 **hit@k / MRR** 与延迟

### 3.2 在线 RAG 评测 `backend/scripts/evaluate_rag.py`

- 对真实 ChromaDB 语料跑完整检索链路（向量 + BM25 + RRF + 重排）
- 输出 **hit@1 / hit@3 / hit@5 / MRR**，明细落盘 CSV
- 评测集 `scripts/eval_questions.json`：22 个问题，覆盖 3 个知识库

### 3.3 自建中文评测知识库

- 22 篇中文技术文档，3 个知识库（后端基础 / AI 应用 / 项目经验）
- 每篇 500~1500 字，涵盖 Redis、MySQL、消息队列、分布式事务、JVM、RAG、Prompt 等主题
- 文档位于 `backend/data/interview_kb/`，导入脚本 `scripts/import_kb.py`

## 4. 发现的问题与根因定位

初版评测 hit@1 = **63.6%**，且多个明显强匹配的查询召回失败。逐一排查后定位到 **5 个问题**：

### 问题 1：BM25 中文不切词（检索质量，高优先级）
- **现象**：中文整句被空格分词当成一个 token，关键词检索几乎失效
- **根因**：`rank_bm25.BM25Okapi` 默认按空格切分，对无空格的中文文本退化为整句匹配
- **修复**：引入 **jieba 中文分词 + 基础停用词过滤**

### 问题 2：top_k_bm25 配置未生效（检索质量）
- **现象**：`TOP_K_BM25=20` 配置从未生效
- **根因**：代码误用 `settings.top_k_vector` 而非 `settings.top_k_bm25`
- **修复**：改为读取 `top_k_bm25`

### 问题 3：英文重排模型对中文打分失效（检索质量，**本次最关键的发现**）
- **现象**：向量检索与 BM25 均已把正确文档排第 1，但重排后正确文档被挤出 Top-5；例如查询"线程池的核心参数怎么设置？"，正确文档在两个召回源中都排第 1，最终 Top-5 却全是无关文档
- **根因**：`cross-encoder/ms-marco-MiniLM-L-6-v2` 是英文模型，中文经其 tokenizer 后大部分变成 `[UNK]`，对任意中文对打分近似恒定（实测 7.37~7.66 挤在一起），重排不仅无益反而破坏排序
- **修复**：替换为**中文优化的重排模型** `maidalun1020/bce-reranker-base_v1`，修复后对中文能正确区分相关/无关（实测相关 0.679 vs 无关 0.413）

### 问题 4：索引全量重建导致查询延迟随语料线性增长（性能）
- **现象**：每次查询都执行「全量拉取向量库语料 + 分词 + 重建 BM25 索引」
- **根因**：检索实现未做任何缓存，语料规模越大延迟越高
- **修复**：
  - 语料缓存：`VectorStore` 增加 TTL 缓存（30s）+ `texts_revision` 版本号，增删文档显式失效
  - 索引缓存：BM25 索引按版本号重建，仅文档变更时重建一次，稳态查询只做打分

### 问题 5：历史测试文档污染检索（数据质量）
- **现象**：早期验证遗留的 `rag_test.txt` 在 22 个问题中 12 次进入 Top-5，甚至对"线程池"查询排第 1
- **修复**：删除该测试文档，检索空间回归纯净

## 5. 量化结果

### 5.1 检索质量（真实知识库，22 个问题 / 3 个知识库 / 22 篇文档）

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| hit@1 | 63.6% | **100%** |
| hit@3 | 77.3% | **100%** |
| hit@5 | 77.3% | **100%** |
| MRR | 68.9% | **100%** |

> 注：上表为「旧分块器」下的结果（每篇 1 块，关键词必在块内）。升级为结构感知分块后（见 5.5），demo 语料 hit@1 = 90.9% / MRR = 93.2%——因长文档被切细，关键词可能落在非 Top-5 兄弟块；但对真实长文档（制度文件/技术手册）结构感知分块明显更优，属预期权衡。

### 5.2 检索质量（合成演示语料，8 组问答，用于展示 jieba 分词收益）

| 指标 | 旧 BM25（空格分词） | 新 BM25（jieba 分词） |
|------|--------------------|----------------------|
| hit@1 | 12.5% | **100%** |
| MRR | 12.5% | **100%** |

### 5.3 检索延迟（稳态单次查询，含打分）

| 语料规模 | 旧·每查询重建索引 | 新·缓存复用 | 新·冷启动建索引（仅文档变更时一次） |
|---------|------------------|------------|----------------------------------|
| 1,000 块 | 2.2 ms | 1.0 ms | 124 ms |
| 10,000 块 | 36.9 ms | 16.3 ms | 1.2 s |
| 50,000 块 | 127.8 ms | 101 ms | 7.6 s |

> 说明：旧实现每查询还额外承担全量 ChromaDB 网络拉取，本表仅计入 CPU 成本，真实差距更大；「索引重建」是本次优化的核心——从每查询支付一次变为仅文档变更支付一次。

### 5.5 分块策略升级（结构感知分块）

**问题**：旧分块把 `\n\n` 压成 `\n` 丢失段落结构；overlap 用「4 字符≈1 token」字符估算；表格/代码块/标题无针对性处理；无块级质量校验。

**升级**（`services/chunking.py`）：
- 保留段落边界，先按结构单元切分再贪心累积
- 标题（H1-H6）作天然切分点；代码块、表格作原子单元不切断
- overlap 用 tiktoken **精确数 token**，不再字符估算
- 块级质量校验：过滤近空块、合并过短块（<50 token）、标记过长块（>1024 token）

**A/B 实验**（`scripts/benchmark_chunking.py`，22 篇语料 / 22 问）：

| 参数 | 块数 | 平均tok | hit@1（向量检索） | MRR |
|------|------|--------|-----------------|-----|
| 256/32 | 107 | 97 | 54.5% | 66.1% |
| **512/64** | 36 | 290 | **86.4%** | 89.3% |
| 768/96 | 31 | 336 | 90.9% | 93.0% |

**结论**：切太细（256）会把同一知识点拆散导致命中率明显下降；512/64 为较稳的通用默认，且有数据支撑而非拍脑袋。真实语料应按自己的文档类型跑 benchmark 再定参。

## 7. 复现步骤

```bash
# 1. 启动基础设施与后端
docker-compose up -d postgres redis chromadb
cd backend && venv\Scripts\activate
alembic upgrade head
uvicorn main:app --reload --port 8080          # 另开终端：python Celery.py

# 2. 导入评测知识库（22 篇 / 3 库）
venv\Scripts\python.exe -X utf8 scripts\import_kb.py

# 3. 运行在线评测（真实语料 hit@k / MRR）
venv\Scripts\python.exe -X utf8 scripts\evaluate_rag.py scripts\eval_questions.json

# 4. 运行离线基准（jieba vs 旧 BM25）
venv\Scripts\python.exe -X utf8 scripts\benchmark_retrieval.py
```

## 8. 总结

本次优化围绕一条主线：**先建评测，再谈优化**。

1. **评测先行**：从零搭建离线基准 + 在线 hit@k/MRR 评测 + 自建中文知识库，让检索质量可量化、可回归
2. **根因定位**：通过分阶段排查，发现英文重排模型对中文失效这一隐蔽问题——向量与 BM25 均排对，重排却破坏排序
3. **修复验证**：jieba 分词、top-k 配置修正、中文重排模型、索引缓存四管齐下，hit@1 由 63.6% 提升至 100%（旧分块）；升级结构感知分块后 demo 语料为 90.9%，但对真实长文档更优；索引重建成本从每查询一次降为文档变更时一次
4. **工程沉淀**：评测脚本、批量导入脚本、测试用例均已沉淀在仓库，可随时复现

**核心经验**：检索系统里"模型语言与语料不匹配"比"参数调得不够好"影响更大；任何声称的优化，都要有可复现的数字背书。
